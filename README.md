# Реквизит-контроль

Учебный мини-проект команды **KIB-35** по дисциплине «Безопасность предпринимательской деятельности» (НИУ ВШЭ, 2026), Блок 2.

**Прототип:** https://claude.ai/artifact/Gk9LvUWGyVazAmfdACHZs8 — перед сдачей открыть доступ по ссылке через меню «Поделиться». Резервный вариант: файл `rekvizit-kontrol.html` открывается в любом браузере без интернета и установки.

## 1. Проблема и пользователь

Для **бухгалтера малого или среднего бизнеса** в **процессе оплаты поставщикам** существует проблема: приходят письма, звонки и сообщения с просьбой срочно сменить реквизиты оплаты. Злоумышленники выдают себя за поставщика или руководителя: пишут с похожего или взломанного адреса, звонят синтезированным голосом, торопят и просят не перезванивать. Это приводит к **переводу денег мошенникам**, которые почти невозможно вернуть.

Команда проверяет, может ли **веб-ассистент, который сверяет запрос со справочником контрагентов, оценивает риск по красным флагам и ведёт бухгалтера по процедуре обратного звонка**, снизить долю пропущенных мошеннических запросов. Ограничение: работа только на синтетических данных, без интеграции с банком и учётной системой.

Пара для реестра тем: **платёжный процесс бухгалтерии МСБ + проверка запросов на изменение реквизитов**.

## 3. Решение

Одностраничное веб-приложение с четырьмя вкладками.

1. **Проверка запроса.** Бухгалтер выбирает контрагента из справочника и вносит:
   - канал, по которому пришёл запрос;
   - адрес отправителя и телефон;
   - текст письма;
   - новые реквизиты.

   Инструмент выдаёт:
   - оценку в баллах и уровень риска;
   - действие;
   - список сработавших признаков с объяснением и ссылкой на источник.

   Затем бухгалтер проходит чек-лист обратного звонка и записывает решение: «Приостановить», «Подтверждено» или «Отклонить». Подтвердить реквизиты без звонка по номеру из справочника нельзя. При высоком риске дополнительно нужно второе согласование.
2. **Тестовый набор.** 30 синтетических запросов прогоняются через движок, считаются полнота, доля ложных тревог и матрица ошибок. Порог можно двигать ползунком.
3. **Справочник контрагентов** — 8 вымышленных поставщиков с ИНН, доменом, телефоном и реквизитами из договора.
4. **Как это работает** — правила, источники и ограничения.

### Логика оценки

Правила прозрачные и детерминированные: каждый признак добавляет баллы.

| Признак | Баллы |
|---|---|
| Домен-двойник или буквы другого алфавита в адресе | +40 |
| ИНН получателя не совпадает с ИНН контрагента | +30 |
| Бесплатная почта или чужой домен у корпоративного контрагента; другой ящик у ИП | +30 |
| Просьба о секретности или запрет звонить | +25 |
| Контрольный ключ счёта не сходится с БИК; неверный формат счёта; счёт физлица (408…) | +25 |
| Получателя нет в справочнике; банк за рубежом; звонок не с номера из справочника; оплата «представителю» | +20 |
| Новый номер телефона для связи; неверный БИК | +15 |
| Давление сроком; типичная легенда (арест, проверка, санкции, смена банка); мессенджер; неверная контрольная сумма ИНН | +10 |

Уровни риска:
- **0–24 балла** — низкий риск;
- **25–49** — требует проверки, оплата приостанавливается;
- **от 50** — высокий риск: не платить, сообщить руководителю.

Правила проверки реквизитов:
- **Счёт** проверяется по контрольному ключу Банка России: последние три цифры БИК плюс 20 цифр счёта, веса 7-1-3, сумма должна делиться на 10.
- **ИНН** проверяется по контрольной сумме.
- **Домен-двойник** определяется по расстоянию Левенштейна (не больше 2) или по названию компании внутри чужого домена.
- **Подмена букв** — по наличию нелатинских символов.
- **Стандартная подпись «письмо конфиденциально»** просьбой о секретности не считается. Это отдельный тест-ловушка T27.

### Метрика успеха и результат

Цель: на наборе из 30 запросов (15 мошеннических, 15 законных) находить **не меньше 90%** мошеннических при доле ложных тревог **не больше 20%**. Одна проверка должна занимать до 2 минут.

Результат при пороге 25 баллов:
- полнота — 15 из 15 (100%);
- ложные тревоги — 0 из 15 (0%);
- средний балл мошеннических запросов — 62, законных — 4.

Ближе всего к порогу:
- мошеннический T09 — взломанный ящик с настоящего домена, 35 баллов;
- законный T29 — филиал в Казахстане, 20 баллов.

**Оговорка.** Правила и тестовый набор составила одна команда, поэтому результат завышен. Нужна проверка на запросах, которых команда не видела (см. план развития).

### Альтернативные площадки

- **Show HN.** Наш поиск не нашёл запусков по этой теме за 2026 год. Площадка ориентирована на разработчиков, а наш пользователь — бухгалтер.
- **Профильные сообщества** — аналог профильного сабреддита: форум «Клерк», Telegram-каналы бухгалтеров. Там пользователи уже обсуждают проблему. Тема смены реквизитов регулярно поднимается в англоязычных материалах для бухгалтерии ([Bitdefender](https://www.bitdefender.com/en-au/blog/hotforsecurity/supplier-bank-details-changed-scam), [Stampli](https://www.stampli.com/resources/bec-payment-diversion-fraud/)).
- **BetaList** подходит для набора ранних тестировщиков до публичного запуска.

Обзор LaunchList опубликован поставщиком собственного launch-сервиса, поэтому как доказательство спроса мы его не используем.

### Выводы для проекта

1. **Ценность формулируется через момент «до того, как деньги ушли».** Так говорят все три запуска: *before money leaves*, *before it leaves your account*. Наше обещание: «Проверьте запрос на смену реквизитов до оплаты».
2. **Аудитория узкая и привязана к рабочему инструменту.** Это бухгалтеры на конкретной учётной системе (Xero, QuickBooks), им обещают быстрый старт и бесплатный тариф. Для российского МСБ такой системой была бы 1С. В MVP интеграции нет, зато прототип запускается в браузере без регистрации.
3. **Демо — скриншоты, отклик на Product Hunt слабый (0–3 голоса), главный вопрос аудитории — доверие.** Автор Xeltra прямо спрашивает, что нужно, чтобы доверять такому инструменту. Поэтому наш прототип объясняет каждый балл и ссылается на источник. Гипотезу разумнее проверять в профильных сообществах бухгалтеров, а не на Product Hunt.

**Незакрытый разрыв.** Решения уровня Trustpair и Eftsure рассчитаны на крупный бизнес с ERP и стоят денег. Инструменты для малого бизнеса привязаны к Xero/QBO, которых нет в российской практике. Бесплатные чек-листы не автоматизируют проверку. Простого русскоязычного инструмента для бухгалтера МСБ нет, а нужен он такой:
- работает без интеграции;
- учитывает российские реквизиты: контрольный ключ счёта по БИК, ИНН, счета физлиц 408…;
- объясняет каждый признак;
- не даёт подтвердить реквизиты без звонка.

## 7. Как воспроизвести демо (3–5 минут)

1. Открыть прототип по ссылке или файл `rekvizit-kontrol.html` в браузере.
2. **Сложный случай T09.** Он загружен при открытии: письмо с настоящего домена, но с новым телефоном, «проверкой банка» и сроком «до конца дня». Итог — 35 баллов, «Требует проверки». Показать, что кнопка «Реквизиты подтверждены» не срабатывает без отметки о звонке по номеру из справочника.
3. **T01** (выбрать в списке примеров) — домен `po1arsnab.test` с цифрой 1 вместо буквы l. Итог — 50 баллов, высокий риск.
4. **T03** — в домене кириллическая «е», визуально неотличима. Итог — 65 баллов.
5. **Ловушка T27.** Законное письмо со стандартной подписью «сообщение конфиденциально» даёт 0 баллов, ложной тревоги нет.
6. **Вкладка «Тестовый набор».** Полнота 100%, ложные тревоги 0%. Подвигать ползунок порога: при 45 баллах полнота падает, при 15 появляются ложные тревоги.
7. **Своя проверка.** «Очистить форму» → выбрать контрагента → вписать свой вымышленный запрос → «Проверить запрос».

Пересобрать данные и движок с нуля:

```
python3 gen.py         # создаёт data.json: 8 контрагентов, 30 запросов с корректными контрольными суммами
node -e "const RK=require('./engine.js'),d=require('./data.json');const e=RK.evaluate(d.cases,d.vendors);console.log(e.tp,e.fn,e.fp,e.tn)"
```

## 9. Ограничения и план развития

**Ограничения:**
- набор тестов составлен той же командой, что и правила;
- взломанный ящик без других ошибок может набрать мало баллов, поэтому звонок обязателен всегда;
- нет проверки заголовков письма (SPF, DKIM, DMARC) и банковских справочников БИК.

**План развития:**
1. Собрать 20–30 новых синтетических запросов силами другой команды и измерить метрику повторно.
2. Добавить разбор заголовков письма: файл .eml, SPF, DKIM, DMARC.
3. Загружать справочник контрагентов из CSV или выгрузки 1С.
4. Сверять БИК с официальным справочником Банка России.
5. Добавить отчёт для руководителя по журналу решений.

## 10. Данные и безопасность

Используются только синтетические данные:
- компании, телефоны, банки, ИНН и счета вымышлены;
- домены в зоне `.test`, зарезервированной для тестов (RFC 2606);
- адреса на бесплатных почтовых сервисах придуманы для примеров.

Реальные персональные данные не собираются, внешние запросы не выполняются, введённые данные не покидают браузер. Журнал решений хранится только в браузере пользователя.
